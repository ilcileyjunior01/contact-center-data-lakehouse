1. Visão Geral da Arquitetura

Um Data Lakehouse combina o armazenamento barato do Data Lake (S3) com as capacidades analíticas do Data Warehouse (Iceberg com ACID e SQL). O dado percorre 3 camadas — chamadas de Medallion Architecture:

💡

Por que Lakehouse? Data Lake (S3) = armazenamento barato, qualquer formato, qualquer escala. Data Warehouse (Iceberg) = ACID, MERGE INTO, schema, queries SQL. O Lakehouse usa os dois juntos: grava no S3 mas trata como banco de dados.

1
Carga no Bronze (S3)
Script: pipeline/ingestion/s3_data_loader.py

O script lê os CSVs e grava como Parquet particionado no S3, simulando o que o Kinesis Firehose faria em produção.

Por que Parquet e não CSV?

  • CSV: texto puro, sem tipos, lento para ler
  • Parquet: formato colunar — lê só as colunas necessárias
  • Snappy: compressão de ~70% sem custo de CPU elevado
  • Glue/Athena leem Parquet 10× mais rápido

Por que particionar por ano/mes/dia?

  • Athena paga por TB lido — particionar reduz custo
  • Consulta de janeiro 2024 → vai direto a ano=2024/mes=1/
  • Ignora todos os outros meses (partition pruning)
  • Glue Crawler descobre partições automaticamente

Estrutura resultante no S3:

s3://act-cc-dev-lakehouse/
└── bronze/
    └── operacao/
        └── chamada/
            └── ano=2024/
                └── mes=1/
                    └── dia=10/
                        └── chamada_20240110.parquet  ← nosso registro aqui
2
Glue Crawler Cataloga o Bronze
Serviço: AWS Glue Crawler + EventBridge + Lambda

Quando um arquivo Parquet chega no S3, a cadeia event-driven dispara automaticamente:

  1. S3 PutObject — arquivo chegou em bronze/operacao/chamada/
  2. EventBridge — detecta o evento S3 e aciona a Lambda
  3. Lambda fn_start_glue_crawler — identifica qual tabela é pelo prefixo do path e inicia o crawler correspondente
  4. Glue Crawler — lê o Parquet, descobre o schema (colunas, tipos, partições)
  5. Glue Data Catalog — registra a tabela db_bronze.chamada com schema completo
ℹ️

Por que o Crawler é necessário? Os jobs PySpark usam glue_context.create_dynamic_frame.from_catalog(database="db_bronze", table_name="chamada") — sem o Catalog, o job não saberia onde está o dado nem qual é o schema. O Crawler é quem registra essa informação.

Antes de ler qualquer dado, o job pergunta: "Qual foi o último registro que já processei?"

3.3 — Interpretação do CDC

Transforma a coluna Op (letra bruta do DMS) em texto legível:

df_cdc = (
    df_bronze
    .withColumn("dt_cdc_evento", F.to_timestamp(F.col("_timestamp")))
    .withColumn("op_cdc",
        F.when(F.col("Op") == "I", F.lit("INSERT"))   # ← "Op" com O MAIÚSCULO
         .when(F.col("Op") == "U", F.lit("UPDATE"))
         .when(F.col("Op") == "D", F.lit("DELETE"))
         .otherwise(F.lit("UNKNOWN")))
)
🐛

Bug crítico corrigido: O DMS gera a coluna como "Op" (O maiúsculo). Um job usava F.col("op") (minúsculo) — o Spark não encontrava a coluna e todos os registros viravam "UNKNOWN", quebrando silenciosamente o pipeline. Corrigido no job_tb_jornada_operador_bronze_to_silver.py.

3.4 — Deduplicação CDC

Um mesmo registro pode ter múltiplos eventos CDC. Precisamos ficar com o mais recente.

window_dedup = Window.partitionBy("id_chamada").orderBy(F.col("dt_cdc_evento").desc())

df_dedup = (
    df_cdc
    .withColumn("_row_num", F.row_number().over(window_dedup))
    .filter(F.col("_row_num") == 1)           # só o mais recente por PK
    .drop("_row_num", "Op", "_timestamp")    # remove colunas técnicas
)

3.5 — Transformações de Negócio

df_transformed = (
    df_dedup
    # 1. Cast dos tipos: string → tipos corretos
    .withColumn("id_chamada", F.col("id_chamada").cast(LongType()))
    .withColumn("dt_inicio",  F.to_timestamp(F.col("dt_inicio"), "yyyy-MM-dd HH:mm:ss"))
    .withColumn("dt_fim",     F.to_timestamp(F.col("dt_fim"),    "yyyy-MM-dd HH:mm:ss"))

    # 2. Normalização de texto
    .withColumn("st_chamada", F.upper(F.trim(F.col("st_chamada"))))
    .withColumn("st_chamada", F.coalesce(F.col("st_chamada"), F.lit("DESCONHECIDO")))

    # 3. Métricas derivadas
    .withColumn("nr_duracao_minutos", F.round(F.col("nr_duracao_segundos") / 60.0, 2))

    # 4. Flags de negócio (SMALLINT: 0 ou 1)
    .withColumn("fl_duracao_valida",
        F.when(F.col("nr_duracao_segundos") > 0, F.lit(1)).otherwise(F.lit(0)).cast("smallint"))
    .withColumn("fl_chamada_completa",
        F.when(F.col("st_chamada").isin("ATENDIDO", "FINALIZADO"), F.lit(1))
         .otherwise(F.lit(0)).cast("smallint"))
)

3.6 — Hash MD5 (Idempotência)

Gera uma "impressão digital" do registro para detectar mudanças:

.withColumn("hash_registro",
    F.md5(F.concat_ws("|",
        F.coalesce(F.col("id_chamada").cast("string"), F.lit("")),
        F.coalesce(F.col("st_chamada"),               F.lit("")),
        F.coalesce(F.col("nr_duracao_segundos").cast("string"), F.lit("")),
        F.coalesce(F.col("dt_inicio").cast("string"),  F.lit("")),
    )))
✅

Para que serve: se esse mesmo registro for reprocessado amanhã sem mudança, o MD5 será idêntico. O MERGE vai comparar target.hash != source.hash e não vai fazer UPDATE desnecessário. O job pode rodar 10 vezes com os mesmos dados — o resultado é sempre o mesmo. Isso é idempotência.

Job Silver → Gold (Dimensões)
11 jobs de dimensões — todos independentes entre si, rodam em paralelo

Antes de gravar os fatos, as dimensões precisam existir. Elas são tabelas de "quem", "onde", "o quê" com surrogate keys.

# Exemplo: job_dim_status_chamada_gold.py
df_silver = spark.table("glue_catalog.db_silver.chamada")
                 .filter(F.col("op_cdc") != "DELETE")  # ignora deletados

df_dim = (
    df_silver
    .select("st_chamada").distinct()   # valores únicos

    .withColumn("sk_status_chamada",
        F.row_number().over(Window.orderBy("st_chamada")))  # surrogate key

    .withColumnRenamed("st_chamada", "ds_status")

    .withColumn("fl_chamada_concluida",
        F.when(F.col("ds_status").isin("ATENDIDO", "FINALIZADO"), F.lit(1))
         .otherwise(F.lit(0)).cast("smallint"))
)

# Registro padrão para JOINs que não encontram a dimensão
df_unknown = spark.createDataFrame([(-1, "DESCONHECIDO", 0)],
    ["sk_status_chamada", "ds_status", "fl_chamada_concluida"])
df_dim = df_unknown.union(df_dim)

ℹ️

Por que sk = -1 "DESCONHECIDO"? Se um fato tiver um status que não existe na dimensão, o LEFT JOIN retornaria NULL. Com o registro padrão sk = -1, o JOIN retorna -1 em vez de NULL — mantendo integridade referencial sem causar erros de NOT NULL ou confusão na análise.

Nas dimensões, row_number() é seguro porque dimensões têm poucos registros (centenas/milhares). O Spark consegue ordenar tudo sem risco de OutOfMemory.

Job Silver → Gold (Fatos)
Script: pipeline/silver_to_gold/job_fato_chamada_gold.py

Os fatos são o "o que aconteceu" — cada linha é um evento (chamada, ticket, chat) com métricas e referências para as dimensões.

5.1 — Resolver Surrogate Keys via LEFT JOIN

df_fato = (
    df_chamada   # Silver

    # sk_cliente: busca pela natural key id_cliente
    .join(df_dim_cliente, df_chamada["id_cliente"] == df_dim_cliente["nk_cliente"], how="left")

    # sk_data: busca pela data de dt_inicio
    .join(df_dim_data, F.to_date(df_chamada["dt_inicio"]) == df_dim_data["dt_completa"], how="left")

    # sk_status: busca pelo valor do status
    .join(df_dim_status, df_chamada["st_chamada"] == df_dim_status["ds_status"], how="left")

    # Se JOIN não encontrou → usa -1 ("DESCONHECIDO")
    .withColumn("sk_cliente",        F.coalesce(F.col("sk_cliente"),        F.lit(-1)))
    .withColumn("sk_data_inicio",   F.coalesce(F.col("sk_data"),           F.lit(-1)))
    .withColumn("sk_status_chamada", F.coalesce(F.col("sk_status_chamada"), F.lit(-1)))
)

5.2 — Gerar Surrogate Key do Fato

.withColumn("sk_chamada", F.monotonically_increasing_id())  # BIGINT

❌ row_number() — PROBLEMA

row_number().over(Window.orderBy("id")) sem partitionBy força o Spark a coletar todos os dados em uma única partição para poder ordenar globalmente.

Com milhões de linhas → OutOfMemory no driver.

✅ monotonically_increasing_id() — SOLUÇÃO

Gera IDs únicos distribuídos entre os executores. Não precisa de shuffle global.

Retorna BIGINT. Pode gerar valores como 8589934592 (não sequencial, mas único).

5.3 — MERGE INTO no Fato

spark.sql("""
    MERGE INTO glue_catalog.db_gold.fato_chamada AS target
    USING stg_fato_chamada AS source
    ON target.nk_chamada = source.nk_chamada  -- usa NATURAL KEY, não SK!
    WHEN MATCHED THEN UPDATE SET *
    WHEN NOT MATCHED THEN INSERT *
""")
⚠️

Por que nk_chamada e não sk_chamada? O sk_chamada muda a cada execução (monotonically_increasing_id() gera um novo número). A nk_chamada (natural key = id original do sistema fonte) é estável — representa sempre a mesma chamada. Usar o SK no MERGE causaria duplicatas.

Consulta Analítica (Athena)
Amazon Athena — SQL serverless sobre S3 + Iceberg

O dado está pronto. Um analista abre o Athena e consulta diretamente:

-- Volume e TMA de chamadas por fila e data
SELECT
    d.nr_ano,
    d.nr_mes,
    d.nr_dia,
    f.nm_fila,
    COUNT(*)                                      AS total_chamadas,
    ROUND(AVG(c.nr_duracao_segundos) / 60.0, 2)  AS tma_minutos,
    SUM(c.fl_chamada_completa)                    AS chamadas_completas
FROM   db_gold.fato_chamada  c
JOIN   db_gold.dim_data      d ON c.sk_data_inicio = d.sk_data
JOIN   db_gold.dim_fila      f ON c.sk_fila        = f.sk_fila
WHERE  d.nr_ano = 2024 AND d.nr_mes = 1
GROUP BY d.nr_ano, d.nr_mes, d.nr_dia, f.nm_fila
ORDER BY d.nr_dia, total_chamadas DESC;
ℹ️

Partition Pruning: o WHERE com nr_ano=2024 AND nr_mes=1 faz o Athena ler apenas as partições ano=2024/mes=1/ — ignora todos os outros meses. Isso reduz o custo (paga por TB lido) e o tempo de resposta.

10. Perguntas Frequentes em Entrevista

❓ Por que Iceberg e não Delta Lake ou Hudi?

Iceberg tem integração nativa com AWS Glue e Athena. O Glue 4.0 suporta Iceberg com a flag --datalake-formats iceberg sem precisar instalar JARs externos. Delta Lake exige JARs proprietários da Databricks. Para stack 100% AWS, Iceberg é a escolha natural.

❓ Como você garante que um job pode rodar duas vezes sem duplicar dados?

Duas camadas de proteção: (1) o watermark filtra registros já processados antes mesmo de ler o dado. (2) o MERGE INTO com hash_registro garante que um registro não alterado não seja atualizado desnecessariamente. Mesmo que o job rode 10 vezes com os mesmos dados, o resultado é sempre idêntico — isso é idempotência.

❓ O que acontece se um registro chegar com id_chamada nulo?

O job calcula _motivo_quarentena = "id_chamada_nulo" e grava o registro em s3://bucket/quarantine/tb_chamada/ particionado por data de ingestão. O job não falha — os dados válidos continuam sendo processados normalmente. Analistas podem investigar os registros de quarentena depois.

❓ Por que monotonically_increasing_id() nos fatos e não row_number()?

row_number() sem partitionBy em tabelas fato com milhões de linhas força o Spark a coletar todos os dados em uma única partição para ordenar globalmente — risco real de OutOfMemory em produção. monotonically_increasing_id() gera IDs únicos distribuídos entre os executores sem shuffle global, retorna BIGINT e funciona em qualquer escala. O MERGE usa a natural key (nk_*), então a estabilidade do SK não é necessária.

❓ Como você lida com DELETE no CDC?

Na Silver, o campo op_cdc recebe "DELETE". Os dados continuam na Silver para auditoria e rastreabilidade. Na Gold, os jobs filtram op_cdc != "DELETE" antes de processar — registros deletados não entram no star schema.

❓ Qual o custo estimado do projeto?

Menos de $8/mês em escala de demonstração. Glue Jobs (~$3,20) e Redshift Serverless (~$3,00) são os maiores custos. A maior economia é substituir DMS + Kinesis (~$24/mês) pelo s3_data_loader.py em modo demo. Parquet + Snappy + particionamento reduz custo de Athena em ~70% vs CSV.

❓ O que é o Glue Data Catalog e por que é necessário?

É o repositório central de metadados — sabe onde cada tabela está no S3, quais são as colunas, os tipos de dado e as partições. Sem ele, cada job precisaria saber o path físico do S3 e o schema explicitamente. Com o Catalog, qualquer serviço (Glue, Athena, Redshift Spectrum, EMR) consulta pela referência lógica db_bronze.chamada e encontra tudo automaticamente.

❓ Por que usar Surrogate Key (sk_) em vez da chave original?

A chave original do sistema fonte (natural key) pode mudar, ser reutilizada ou não existir para registros de "DESCONHECIDO". O SK é gerado pelo DW, é estável, imutável e permite o registro padrão sk = -1 para integridade referencial. Manter o nk_* na tabela fato garante rastreabilidade até o sistema fonte.
