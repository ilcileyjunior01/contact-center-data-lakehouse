2. Glossário de Termos de Negócio — Contact Center

Antes de mergulhar no pipeline técnico, entenda o vocabulário do domínio. Um engenheiro de dados que não conhece os termos de negócio não consegue modelar os dados corretamente nem conversar com os stakeholders.

TMA — Tempo Médio de Atendimento

Duração média das chamadas efetivamente atendidas. Principal indicador de eficiência operacional do operador.

AVG(nr_duracao_minutos) WHERE fl_duracao_valida = 1
Meta típica: 3–6 min (varia por segmento)

TME — Tempo Médio de Espera

Tempo médio que o cliente aguarda na fila antes de ser atendido. Alta correlação com taxa de abandono — quanto maior o TME, mais clientes desligam.

Meta típica: < 60 segundos

Nível de Serviço

Percentual de chamadas atendidas sobre o total que entrou na fila (atendidas + abandonadas). Indicador primário do contact center.

atendidas / (atendidas + abandonadas) × 100
Meta padrão: ≥ 80% · fl_meta_nivel_servico

Taxa de Abandono

Percentual de clientes que desligaram antes de serem atendidos. Inversamente proporcional ao Nível de Serviço. Acima de 15% dispara alerta operacional.

fl_alto_abandono = 1 quando > 15%

URA / IVR

Unidade de Resposta Audível. Sistema automatizado que atende o cliente antes do operador, oferecendo menu de opções. Cada interação do cliente com o menu é um registro em fato_ura_navegacao.

Discagem Outbound / Preditiva

O contact center liga proativamente para o cliente (cobrança, venda, pesquisa). O sistema disca e transfere ao operador só quando o cliente atende. Registrado em fato_discagem + dim_campanha.

SLA — Service Level Agreement

Prazo contratual para resolução de um ticket. No pipeline, o padrão é 480 minutos (8h). Configurável por categoria e prioridade.

fl_dentro_sla = 1 se resolvido ≤ 480 min

FCR — First Call Resolution

Percentual de problemas resolvidos no primeiro contato, sem recontato. Mede qualidade e eficiência. Quanto maior o FCR, menor o volume de chamadas repetidas e menor o custo operacional.

CDC — Change Data Capture

Técnica que captura todas as mudanças (INSERT/UPDATE/DELETE) em um banco sem impactar as queries da aplicação. Lê o WAL do PostgreSQL. No pipeline: AWS DMS → Kinesis Firehose → S3 Bronze com coluna Op (I/U/D).

WAL — Write-Ahead Log

Arquivo de log interno do PostgreSQL que registra todas as modificações antes de aplicá-las ao banco. O DMS lê esse log para capturar mudanças sem fazer queries nas tabelas de produção — impacto zero na aplicação.

Medallion Architecture

Padrão de Data Lake em três camadas com qualidade crescente: Bronze (raw), Silver (limpo + validado), Gold (modelado para análise). Qualquer camada pode ser reprocessada a partir da anterior sem acessar a fonte original.

Star Schema — Esquema Estrela

Modelo dimensional com uma tabela fato central e tabelas de dimensão ao redor. Otimizado para queries analíticas (GROUP BY + aggregations). Alternativa: Snowflake Schema (dimensões normalizadas — mais complexo, menos performático para BI).

Surrogate Key vs Natural Key

Natural Key (nk_): id do sistema fonte — pode mudar ou ser reutilizado.
Surrogate Key (sk_): gerada pelo pipeline, imutável, permite registro sentinela sk = -1 para "DESCONHECIDO" garantindo integridade referencial sem NULLs.

Watermark

Registro do maior _timestamp já processado por tabela. Garante leitura incremental — o job só lê registros mais novos que o watermark. Armazenado em s3://bucket/checkpoints/tb_*/watermark.json.

Skill / Habilidade do Operador

Competência do operador (ex.: "Suporte Técnico N2", "Inglês + Português", "Produto X"). O roteamento inteligente direciona o cliente para o operador com o skill adequado. Modelado em dim_skill.

Quarentena

Registros que falharam nas regras de qualidade são isolados em path separado com _motivo_quarentena explicando o problema. O job não falha — dados válidos continuam sendo processados. Analistas revisam e corrigem a quarentena posteriormente.

1. Visão Geral da Arquitetura

Um Data Lakehouse combina o armazenamento barato do Data Lake (S3) com as capacidades analíticas do Data Warehouse (Iceberg com ACID e SQL). O dado percorre 3 camadas — chamadas de Medallion Architecture:

💡

Por que Lakehouse? Data Lake (S3) = armazenamento barato, qualquer formato, qualquer escala. Data Warehouse (Iceberg) = ACID, MERGE INTO, schema, queries SQL. O Lakehouse usa os dois juntos: grava no S3 mas trata como banco de dados.

Carga no Bronze (S3)
GitHub: s3_data_loader.py upload_parquet_to_s3() · L130–L181 particionamento ano/mes/dia · L145–L149

O script lê os CSVs e grava como Parquet particionado no S3, simulando o que o Kinesis Firehose faria em produção.

Por que Parquet e não CSV?

  • CSV: texto puro, sem tipos, lento para ler
  • Parquet: formato colunar — lê só as colunas necessárias
  • Snappy: compressão de ~70% sem custo de CPU elevado
  • Glue/Athena leem Parquet 10× mais rápido

Por que particionar por ano/mes/dia?

  • Athena paga por TB lido — particionar reduz custo
  • Consulta de janeiro 2024 → vai direto a ano=2024/mes=1/
  • Ignora todos os outros meses (partition pruning)
  • Glue Crawler descobre partições automaticamente

Glue Crawler Cataloga o Bronze
Serviço: AWS Glue Crawler + EventBridge + Lambda
GitHub: lambda/fn_start_glue_crawler/lambda_function.py infrastructure/02_setup_glue.py (Crawlers)

Quando um arquivo Parquet chega no S3, a cadeia event-driven dispara automaticamente:

  1. S3 PutObject — arquivo chegou em bronze/operacao/chamada/
  2. EventBridge — detecta o evento S3 e aciona a Lambda
  3. Lambda fn_start_glue_crawler — identifica qual tabela é pelo prefixo do path e inicia o crawler correspondente
  4. Glue Crawler — lê o Parquet, descobre o schema (colunas, tipos, partições)
  5. Glue Data Catalog — registra a tabela db_bronze.chamada com schema completo
ℹ️

Por que o Crawler é necessário? Os jobs PySpark usam glue_context.create_dynamic_frame.from_catalog(database="db_bronze", table_name="chamada") — sem o Catalog, o job não saberia onde está o dado nem qual é o schema. O Crawler é quem registra essa informação.

3.3 — Interpretação do CDC ver L134–L156 no GitHub

Transforma a coluna Op (letra bruta do DMS) em texto legível:

df_cdc = (
    df_bronze
    .withColumn("dt_cdc_evento", F.to_timestamp(F.col("_timestamp")))
    .withColumn("op_cdc",
        F.when(F.col("Op") == "I", F.lit("INSERT"))   # ← "Op" com O MAIÚSCULO

         .when(F.col("Op") == "D", F.lit("DELETE"))
         .otherwise(F.lit("UNKNOWN")))

ℹ️

Atenção ao case-sensitivity: O DMS gera a coluna como "Op" (O maiúsculo). Sempre referencie a coluna com o case exato — F.col("Op") — pois o Spark diferencia maiúsculas de minúsculas e um mismatch faz todos os registros caírem em "UNKNOWN" silenciosamente.

3.6 — Hash MD5 (Idempotência) ver L228–L239 no GitHub

Gera uma "impressão digital" do registro para detectar mudanças:

.withColumn("hash_registro",
    F.md5(F.concat_ws("|",
        F.coalesce(F.col("id_chamada").cast("string"), F.lit("")),
        F.coalesce(F.col("st_chamada"),               F.lit("")),
        F.coalesce(F.col("nr_duracao_segundos").cast("string"), F.lit("")),
        F.coalesce(F.col("dt_inicio").cast("string"),  F.lit("")),
    )))
✅

Para que serve: se esse mesmo registro for reprocessado amanhã sem mudança, o MD5 será idêntico. O MERGE vai comparar target.hash != source.hash e não vai fazer UPDATE desnecessário. O job pode rodar 10 vezes com os mesmos dados — o resultado é sempre o mesmo. Isso é idempotência.

    df_chamada   # Silver

    .join(df_dim_cliente, df_chamada["id_cliente"] == df_dim_cliente["nk_cliente"], how="left")

5.2 — Gerar Surrogate Key do Fato

.withColumn("sk_chamada", F.monotonically_increasing_id())  # BIGINT

❌ row_number() — PROBLEMA

row_number().over(Window.orderBy("id")) sem partitionBy força o Spark a coletar todos os dados em uma única partição para poder ordenar globalmente.

Com milhões de linhas → OutOfMemory no driver.

✅ monotonically_increasing_id() — SOLUÇÃO

Gera IDs únicos distribuídos entre os executores. Não precisa de shuffle global.

Retorna BIGINT. Pode gerar valores como 8589934592 (não sequencial, mas único).

5.3 — MERGE INTO no Fato

spark.sql("""
    MERGE INTO glue_catalog.db_gold.fato_chamada AS target
    USING stg_fato_chamada AS source
    ON target.nk_chamada = source.nk_chamada  -- usa NATURAL KEY, não SK!
    WHEN MATCHED THEN UPDATE SET *
    WHEN NOT MATCHED THEN INSERT *
""")
⚠️

Por que nk_chamada e não sk_chamada? O sk_chamada muda a cada execução (monotonically_increasing_id() gera um novo número). A nk_chamada (natural key = id original do sistema fonte) é estável — representa sempre a mesma chamada. Usar o SK no MERGE causaria duplicatas.

8.1 — Estratégia: TRUNCATE + COPY (Full Refresh)

# L61–L77 — copy_sql() em dag_carga_redshift.py
def copy_sql(table: str, s3_prefix: str) -> str:
    return f"""
        TRUNCATE TABLE {SCHEMA}.{table};

        COPY {SCHEMA}.{table}
        FROM '{GOLD_S3}/{s3_prefix}/'
        IAM_ROLE '{IAM_ROLE}'
        FORMAT AS PARQUET
        SERIALIZETOJSON;
    """

✅ Por que TRUNCATE + COPY?

  • Idempotência: pode rodar N vezes com os mesmos dados Gold no S3 e o Redshift terá sempre o mesmo estado
  • Simplicidade: sem lógica de UPSERT no Redshift — toda a complexidade de deduplicação foi resolvida na camada Gold
  • Performance: COPY Parquet é o método mais rápido de carga em massa no Redshift
  • SERIALIZETOJSON: permite colunas SUPER para campos semi-estruturados

⚠️ Trade-off

O TRUNCATE gera um breve período de indisponibilidade dos dados (downtime da tabela). Para dashboards com SLA de disponibilidade contínua, a alternativa é usar tabelas de staging + SWAP (renomear tabelas atomicamente).

Em escala de demonstração, o TRUNCATE + COPY é aceitável e simples de operar.

O Redshift distribui e ordena fisicamente os dados no disco para otimizar JOINs e filtros frequentes:

-- dim_data: DISTSTYLE ALL (tabela pequena — cópia em todos os nós)
CREATE TABLE IF NOT EXISTS gold.dim_data (
    sk_data           INT          NOT NULL,   -- ex: 20240110

)

SORTKEY(sk_data);      -- range scan eficiente no filtro por data

-- fato_chamada: DISTKEY no sk_operador (coluna mais usada em JOINs)
CREATE TABLE IF NOT EXISTS gold.fato_chamada (
    sk_chamada           BIGINT       NOT NULL,
    nk_chamada           BIGINT,
    sk_cliente           INT          DEFAULT -1,

    fl_duracao_valida    SMALLINT
)

SORTKEY(sk_data_inicio, sk_operador); -- filtros por data + operador são os mais comuns
ℹ️

DISTSTYLE ALL vs KEY: Dimensões pequenas (centenas de linhas) usam DISTSTYLE ALL — o Redshift mantém uma cópia em cada nó, eliminando o shuffle de rede durante os JOINs. Tabelas fato (milhões de linhas) usam DISTSTYLE KEY com a coluna de JOIN mais frequente como DISTKEY — dados co-localizam nos nós e o JOIN ocorre localmente.

16. Guia de Troubleshooting

Os erros mais comuns em produção, com causa raiz identificada e solução prática. Cada problema listado já foi encontrado (ou é previsível) neste pipeline.

⚠️

Regra de ouro: sempre verifique os logs do CloudWatch antes de tentar qualquer correção. O job emite logs JSON estruturados com job_name, run_id, status e motivo_erro.

Problema 1 — Glue Job: OutOfMemoryError no Driver

CampoDetalhe
SintomaJob falha com java.lang.OutOfMemoryError: Java heap space no CloudWatch
Causa raizUso de row_number().over(Window.orderBy(...)) sem partitionBy em tabela fato grande → força coleta de todos os dados no driver
SoluçãoSubstituir por monotonically_increasing_id() nos fatos (já implementado). Para dimensões pequenas, row_number() é seguro. Aumentar --driver-memory no job é paliativo, não solução.

CampoDetalhe

11. Perguntas Frequentes em Entrevista

❓ Por que Iceberg e não Delta Lake ou Hudi?

Iceberg tem integração nativa com AWS Glue e Athena. O Glue 4.0 suporta Iceberg com a flag --datalake-formats iceberg sem precisar instalar JARs externos. Delta Lake exige JARs proprietários da Databricks. Para stack 100% AWS, Iceberg é a escolha natural.

❓ Como você garante que um job pode rodar duas vezes sem duplicar dados?

Duas camadas de proteção: (1) o watermark filtra registros já processados antes mesmo de ler o dado. (2) o MERGE INTO com hash_registro garante que um registro não alterado não seja atualizado desnecessariamente. Mesmo que o job rode 10 vezes com os mesmos dados, o resultado é sempre idêntico — isso é idempotência.

❓ O que acontece se um registro chegar com id_chamada nulo?

O job calcula _motivo_quarentena = "id_chamada_nulo" e grava o registro em s3://bucket/quarantine/tb_chamada/ particionado por data de ingestão. O job não falha — os dados válidos continuam sendo processados normalmente. Analistas podem investigar os registros de quarentena depois.

❓ Por que monotonically_increasing_id() nos fatos e não row_number()?

row_number() sem partitionBy em tabelas fato com milhões de linhas força o Spark a coletar todos os dados em uma única partição para ordenar globalmente — risco real de OutOfMemory em produção. monotonically_increasing_id() gera IDs únicos distribuídos entre os executores sem shuffle global, retorna BIGINT e funciona em qualquer escala. O MERGE usa a natural key (nk_*), então a estabilidade do SK não é necessária.

❓ Como você lida com DELETE no CDC?

Na Silver, o campo op_cdc recebe "DELETE". Os dados continuam na Silver para auditoria e rastreabilidade. Na Gold, os jobs filtram op_cdc != "DELETE" antes de processar — registros deletados não entram no star schema.

❓ Qual o custo estimado do projeto?

Menos de $8/mês em escala de demonstração. Glue Jobs (~$3,20) e Redshift Serverless (~$3,00) são os maiores custos. A maior economia é substituir DMS + Kinesis (~$24/mês) pelo s3_data_loader.py em modo demo. Parquet + Snappy + particionamento reduz custo de Athena em ~70% vs CSV.

❓ O que é o Glue Data Catalog e por que é necessário?

É o repositório central de metadados — sabe onde cada tabela está no S3, quais são as colunas, os tipos de dado e as partições. Sem ele, cada job precisaria saber o path físico do S3 e o schema explicitamente. Com o Catalog, qualquer serviço (Glue, Athena, Redshift Spectrum, EMR) consulta pela referência lógica db_bronze.chamada e encontra tudo automaticamente.

❓ Por que usar Surrogate Key (sk_) em vez da chave original?

A chave original do sistema fonte (natural key) pode mudar, ser reutilizada ou não existir para registros de "DESCONHECIDO". O SK é gerado pelo DW, é estável, imutável e permite o registro padrão sk = -1 para integridade referencial. Manter o nk_* na tabela fato garante rastreabilidade até o sistema fonte.
